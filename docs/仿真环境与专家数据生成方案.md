# SO101 洗漱台仿真环境与专家数据生成方案

设计基准：2026-10-16。**当前已开始实施原型，实际完成程度以实施记录为准。** 本文保留设计目标与分阶段要求，细化 [可选仿真与联合训练](可选仿真与联合训练.md)，任务和成功条件以 [任务与数据规范](任务与数据规范.md) 为准。

实施更新：2026-10-17用户明确要求启动，已建立第一版代码并开始实际生成。本文保留原设计背景与目标；实际完成程度、nominal尺寸、原型320×240图像、排查和结果以 [仿真实施记录](仿真实施记录.md) 为准，下文原规划状态不替代实施证据。

## 1. 推荐方案与边界

建议在本地采用 **MuJoCo + SO101 模型 + 简单刚体场景 + 带人工姿态模板的脚本专家**。专家读取仿真物体真值，规划抓取和放置，再通过六维关节目标驱动机器人完成真实接触操作。每次尝试自动判定、保存失败原因；成功轨迹通过动作回放和数据检查后，才导出为 LeRobot 数据。

```text
实物测量 / 少量人工成功示范
        ↓
场景与可达姿态模板 → 随机初始布局 → 可达性预检查
                                       ↓
                           状态机专家 + 关节目标控制
                                       ↓
                         物理成功检查 → 控制目标回放
                                       ↓
                      数据检查 → LeRobotDataset → 可选联合训练
```

这条路线不需要先训练强化学习专家，也不需要加载 π₀.₅ 生成示范。π₀.₅ 是之后学习这些示范的策略。专家在开发时可能需要人工设置关键姿态或参考少量真机示范，因此项目表述应为“自动生成并筛选专家轨迹”，不能声称完全零人工。

首版保留一个桌面场景、一个抓放技能家族：红/蓝牙刷放左/右杯。先跑通一支牙刷和一个杯的物理操作，再扩展到两支牙刷、两个杯和四种指令。牙膏、软刷毛、流水、真实洗手池与大规模并行仿真暂不进入首版。

仿真属于可选支线：G2 真机小数据训练、保存重载和执行链路通过后，有主线节余再启动。**8h 是首次原型探索上限，不是完整环境、自动专家和训练对照的总工期。** 主线真实数据与 40 次正式真机评测仍优先。

## 3. 先测量、先验证的事项

搭建前形成一张实物测量表；未知项留空，不凭渲染效果猜测：

| 对象 | 需要记录 |
|---|---|
| SO101 | 底座安装位置、实际关节零位/符号/范围、TCP、夹爪开合范围、腕相机外壳尺寸 |
| 牙刷 | 总长、柄宽/厚、刷头尺寸、重量、可夹区域、接触面材质 |
| 杯子 | 内径、外径、杯口高度、底厚、重量、是否在实物中固定 |
| 桌面 | 相对底座高度、边界、杯/牙刷可摆区域 |
| 相机 | top/wrist 内参或近似视场、安装变换、分辨率、镜像/旋转、实际帧率 |

首先用低速遥操作或仿真交互验证以下动作链：

```text
牙刷平放 → 近刷头/颈部抓取 → 试抬 → 转为刷柄朝下
→ 到达杯口 → 柄部入杯 → 松爪 → 撤离 → 静置 2 秒
```

“柄朝下、刷头露在杯外”是建议终态，不要求整支牙刷低于杯沿。优先尝试近刷头抓取，是为了给柄部留出插入长度，并让夹爪避开杯沿；是否可行仍取决于真实牙刷、夹爪和 SO101 姿态。

若平放拾取困难，可调整杯子位置、抓取方向，或使用实物和仿真中都有的小支架。不能只在仿真中把牙刷悬空，以此制造容易抓取的数据。若五关节结构无法完成整个链路，应收缩任务工作区或修改实物布置后重新确认，不能依靠瞬移补足动作。

## 4. 场景如何搭建

### 4.1 坐标系和布局

定义世界 Z 轴向上，桌面为高度基准，记录 SO101 底座相对该坐标系的变换。分别定义 robot_base、TCP、top_camera、wrist_camera、brush、cup 坐标系；写清各轴方向和单位。

初版限定“已验证可达的牙刷区域”和“两块杯子区域”，先用固定布局调通。正式任务的左右依据未镜像的 top 画面，而不是假定某个世界坐标轴的正负；在顶视图中检查两杯的投影与标记，保证移动范围内不交换左右。

不要先给牙刷任意 360° 朝向或把杯子摆满桌面。可达工作区应由抓取、转向、入杯、撤离的完整链路共同确定，而不是只测试 TCP 能否到达一个点。

### 4.2 机器人与控制接口

SO101 模型是 **五个手臂关节加一个夹爪关节**。关节按名称查找，并通过模型中的 qpos/dof/actuator 地址建立索引；加入物体 freejoint 后，不能默认 `qpos[:6]` 就是机器人状态。

计划对外顺序仍为：

```text
shoulder_pan.pos, shoulder_lift.pos, elbow_flex.pos,
wrist_flex.pos, wrist_roll.pos, gripper.pos
```

物理内部保留原始关节角和执行器目标；训练导出采用经过核验的真实接口语义。机械臂映射可从逐关节的符号、比例、零位偏移开始，非线性夹爪单独标定。`rad → deg` 只解决单位，不能自动解决模型零位、安装方向和夹爪范围差异。

用若干双方安全的姿态检查：数值是否对应相同物理姿态、夹爪是否同向开合、动作限幅是否一致。未经这些核对，不直接把仿真控制序列发送到真机。

### 4.3 牙刷：可被真实接触抓起的自由刚体

一支牙刷为一个自由刚体，附带多个简单碰撞几何体：柄可用 capsule/box，颈部和刷头用 box 或其他凸形近似。首版不模拟软刷毛，保留可见颜色和轮廓即可。

测量总质量并检查整体质心、惯量；显式定义惯性或合理分配各碰撞部分质量，避免外观 mesh 和碰撞体重复计入质量。定义刷柄末端、抓取区域、长轴等语义 site，供规划与判定使用。

牙刷在运行期间受重力、夹爪、桌面和杯子的接触影响。只有 reset 和独立规划探针可以设置状态；正式执行不得动态绑定夹爪、关闭重力、隐藏牵引，或逐帧改写牙刷位姿。

### 4.4 杯子：外观中空不代表碰撞中空

建议用“底盘 + 环形排列的多段壁”形成碰撞空腔，外观可另用模型。壁段可从 16～24 段开始试验，段数只是初值；相邻壁需避免漏缝，内腔不能被隐藏碰撞体填满。

MuJoCo 普通 mesh 碰撞采用凸包，因此一个看起来中空的整杯 mesh 可能得到实心碰撞形状。外观 mesh 应关闭碰撞，接触交给分解后的几何体。[MuJoCo mesh 说明](https://mujoco.readthedocs.io/en/stable/XMLreference.html#asset-mesh)

先做两个独立检查：把小物体从杯口落下，确认能进入并停在杯底；让牙刷与杯沿/内壁接触，确认不会穿底、卡进壁缝或在空腔上方悬浮。

如果实物杯子未固定，正式仿真杯子也应是自由刚体，让推动、倾斜和翻倒自然发生。调试时可以固定杯子隔离控制问题，但此类轨迹标注为调试数据，不直接混入最终迁移数据。若实物使用防滑垫或固定架，应在两域同步实现并记录。

### 4.5 图像与接触参数

top 相机固定；wrist 相机固定在实物对应的随臂部件上。初版按项目候选的 640×480 采集，再交给模型处理器 resize/padding；若实际采集方案改变，两域一起更新。

调试中可以显示接触点、坐标轴和目标 site，但保存给策略的 RGB 不包含这些标记、目标高亮或物体 ID。红/蓝身份必须与颜色及指令一致；两个杯子和错误牙刷应留在画面中。

接触摩擦、接触软硬、伺服增益与力矩限制从模型及实测合理范围开始，分别验证静置、夹持、抬升和释放。不通过无限增大摩擦、增益或夹持力来掩盖几何问题；调参后重新跑接触检查并保存配置版本。

## 5. 专家如何产生动作

### 5.1 专家看到什么

脚本专家可以读取机器人状态、目标牙刷/杯子的真值位姿、几何尺寸和接触信息，依据指令选定对象。这属于仿真中的特权信息，用于自动做标注和控制。

训练策略只获得真实系统也有的 **top RGB、wrist RGB、六维本体状态和文本指令**。物体位姿、接触、状态机阶段和成功标签保存在独立诊断中，不意外成为模型输入。

### 5.2 姿态模板 + 受约束 IK + 路径检查

五个手臂关节无法保证任意三维位置与任意三维朝向同时实现。初版建立少量已经验证的“抓取—转向—入杯”姿态模板，针对布局调整位置和允许的小范围方向。模板可来自仿真交互设置或少量人工成功示范。

每个候选先求 TCP 位置，并约束关键轴方向；允许任务无关的剩余旋转及合理容差。可采用阻尼最小二乘，通过 site 的位置/转动 Jacobian 迭代求解，再检查关节边界与 Jacobian 的病态程度。MuJoCo 提供 Jacobian 计算接口，不等于自动提供完整任务 IK 或避障器。[官方 Jacobian API](https://mujoco.readthedocs.io/en/stable/APIreference/APIfunctions.html#mj-jacsite)

不能把“3 个位置 + 2 个方向约束”视为必然有解。抓取时还要满足夹指闭合方向、开口与桌面净空；入杯时还要满足刷柄方向以及夹爪、手腕、腕相机外壳与杯沿的净空。

对每个候选检查整条链路：

1. 抓取前、抓取、抬升、转向、杯上方、插入、撤离均有连续可达解。
2. 无机器人自碰撞、桌面/错误物体碰撞和关节突然跳到另一分支。
3. 抓住牙刷后的路径包含牙刷碰撞体，不能只检查空夹爪。
4. 规划时在独立数据副本中试解；实际执行仅下发关节目标并推进物理。

首版优先少量无障碍关键路径，按关节速度/加速度限制平滑插值，并在足够密的中间点检查碰撞。遇到不可行布局先拒绝并记录；RRT、完整运动规划框架或复杂重抓留到后续，避免初期工作量失控。

### 5.3 状态机与失败条件

阶段转换依赖观测条件和持续时间，不能只按“过了几秒”切换。每阶段设置超时；阈值在原型中标定后冻结。

| 阶段 | 动作 | 通过条件 | 典型失败码 |
|---|---|---|---|
| RESET | 采样布局，物体落稳，机器人回到初态 | 无初始穿插、姿态稳定、布局可行 | invalid_reset / unreachable |
| PREGRASP | 张爪，沿可行方向接近 | 位姿误差与净空达标 | ik_fail / collision |
| CLOSE | 缓慢闭合并短暂保持 | 双指与目标接触，进入试抬验证 | no_grasp / wrong_object |
| LIFT | 小幅试抬，再抬到运输高度 | 目标离桌并随夹爪运动，未明显滑移 | slip / dropped |
| REORIENT | 在净空区域将刷柄转向下方 | 柄部方向可入杯，仍稳定夹持 | pose_unreachable / collision |
| ABOVE_CUP | 将刷柄端移到目标杯口上方 | 端点投影在安全内腔，夹爪/相机有净空 | rim_clearance |
| INSERT | 低速小步下降 | 柄段进入内腔，杯未被明显推动 | rim_hit / cup_moved |
| RELEASE | 张爪释放 | 夹爪不再夹持牙刷，牙刷由杯支撑 | release_failed |
| RETRACT | 沿验证过的方向撤离 | 未带出牙刷，未碰倒杯 | dragged_out / cup_tipped |
| SETTLE | 机器人保持安全姿态 | 连续满足最终条件至少 2 秒 | unstable / timeout |

接触应按 geom/body 身份检查，区分牙刷、杯子和桌面。仅发送“闭合”指令不能证明抓住，接触到桌面也不能当成抓取成功；试抬后检查物体相对夹爪的位姿是否保持稳定。

首版失败即结束该次尝试，保存原因并重新 reset。后续若增加有限重试，必须保存完整过程和重试次数；不能截掉失败前半段后把剩余片段当成一次完整成功。

### 5.4 控制频率和时间对齐

候选控制/记录频率为 30Hz，必须与真实最终方案一致。物理步长可先试 `1/600 s`，每个控制周期 20 个物理子步；这只是待验证配置，需检查接触稳定性和本地速度。

如果沿用资产的其他步长，应采用严格时间调度。例如 `0.005 s` 不整除 `1/30 s`，每帧固定四舍五入子步会使累计时间和标注 FPS 不一致。不能生成 10Hz 动作后仅把 metadata 写为 30Hz。

每个控制时刻采用以下约定：

```text
在 t 时刻读取 state_t 与两路 RGB_t
→ 专家计算并限幅 target_t
→ 保存 observation_t、实际发送的 action_t、timestamp_t
→ 保持/按约定执行 target_t，物理推进到 t+Δt
→ 检查阶段条件，下一周期再采样
```

`action_t` 是真正写入控制接口的目标，包含约定的限幅/平滑结果；不是事后把 `state_(t+1)` 填回来。记录数组应复制当时内容，避免 MuJoCo/NumPy 内存视图在后续步进中被覆盖。[MuJoCo Python 内存说明](https://mujoco.readthedocs.io/en/stable/python.html#basic-usage)

采样边界还应保证派生量与当前 qpos 一致：步进后、读取物体/site/camera 位姿和成功判定前，使用 `mj_forward` 或等价的一致调度，再更新渲染场景。积分后直接混用新 qpos 与旧派生位姿可能造成一物理子步错位；若安装了控制回调，需避免刷新时产生额外有副作用的控制操作。接触异常也应在物理子步中监控，不能只看低频保存帧。[MuJoCo 状态一致性说明](https://mujoco.readthedocs.io/en/stable/computation/index.html#consistency-in-mjdata)

离线生成不必按墙钟实时等待，但仿真时间必须正确；图像慢不会改变模拟中的动作周期。发生丢帧或异步采样时记录真实时间关系，不能重复图片而不标记。

## 6. 成功与轨迹质量如何自动检查

### 6.1 最终成功检查器

检查器独立于专家状态机：专家说“完成”不能直接设置成功。以当前目标杯的局部坐标系计算位置关系，同时满足：

1. 指定牙刷的刷柄末端及一段柄部在杯口下方、真实内腔范围内，保留几何安全余量；刷头允许露在杯外，牙刷允许倾斜。
2. 牙刷由目标杯接触支撑，不是仍被夹爪夹住、穿透杯底或搁在杯旁桌面上。结合杯接触、柄段位置、释放后的重力演化检查，不只靠一个接触标志。
3. 夹爪已打开并撤离；稳定窗口中无夹爪继续支撑，牙刷线/角速度低于冻结阈值，持续至少 2 秒。
4. 杯子未翻倒，位移和倾角在允许范围；错误牙刷未被错误收纳，目标杯身份正确。
5. 整段无数值发散、异常穿透、隐藏辅助或超时。

不能用牙刷质心必须在杯内作为唯一标准：刷头外露时质心可能较高；也不能用 TCP 靠近杯子、二维框重叠或“执行到最后一步”替代物理成功。

容差、允许杯位移、低速阈值和最低柄部插入长度由实物尺寸及试验确定。本文不把未经运行的数值写成验收结果。检查器需有人工构造的正反例：稳定入杯应通过；悬在杯上、夹爪未松、错误杯、刷柄穿底、杯倒、刚入杯随后掉出均应失败。

### 6.2 控制回放与人工抽查

每条拟纳入训练的成功轨迹，从相同模型、物理参数和初始状态重新开始，只重放保存的六维控制目标和时间调度，不运行专家反馈、不逐帧设置物体状态。再次通过成功检查器后，标记 `replay_passed=true`。

保存足够的积分状态、控制器内部状态和场景配置；仅保存 qpos 或随机种子不能保证完整复现。MuJoCo 复现还受版本与状态完整性影响，因此记录 `mj_getState/mj_setState` 使用的 state spec、引擎版本、模型/资产哈希和调度方式。跨机器不以浮点逐位相同为要求，但必须重新检查任务成功。[官方复现说明](https://mujoco.readthedocs.io/en/stable/computation/index.html#reproducibility)

回放通过仍不等于仿真与真实物理一致。初期逐条看视频，之后至少抽查每种指令、每种姿态模板、边界布局和新参数版本；对照图像、接触和曲线排查滑移、杯沿卡住或过于依赖不合理摩擦的成功。

建议数据筛选流水线为：

```text
reset 合法 → 路径可行 → 动态执行成功 → 控制回放成功
→ 图像/数值/时序检查 → 人工抽查 → qualified 清单
```

不合格轨迹仍保留诊断，首版模仿学习只使用筛选后的成功 episode。保留拒绝率及失败原因，避免把“只统计通过筛选的数据”误报为专家对任意布局的成功率。

## 7. 原始轨迹和 LeRobot 数据如何保存

### 7.1 原始记录优先于直接写训练数据

建议每次尝试先写独立原始目录，再由导出器读取合格清单生成数据集。以下目录是建议结构，**当前尚未创建对应实现或数据**：

```text
data/sim/raw/<scene_version>/<attempt_id>/
  metadata.json          # 指令、来源、版本、seed、布局、参数、阶段结果
  initial_state.npz      # 完整相关初始状态及 state spec
  trajectory.npz         # timestamps、qpos/qvel、raw ctrl、映射后 state/action
  images/top/...         # 或同时间索引的无损缓存，导出后可按规则清理
  images/wrist/...
  diagnostics.jsonl      # 接触、物体位姿、阶段、异常，仅用于审查

data/sim/lerobot/<dataset_version>/  # 由冻结版本 LeRobot writer 生成
outputs/sim/<run_id>/
  attempts.jsonl         # 包含拒绝、失败、成功，不只保存成功数
  qualified.json        # 通过全部门槛的 attempt/episode 清单
  validation.json       # 回放、重读、抽查结果
  summary.json          # 尝试数、有效数、原因分布、速度、磁盘量
```

所有大体积文件保存在已忽略的数据/输出位置，代码仓库保留场景、配置、检查规则和小型汇总。若开启随机物理/视觉参数，保存每次实际取值，不能只记一个总 seed。

### 7.2 策略输入输出与独立元数据

| 字段 | 内容 | 是否交给策略 |
|---|---|---|
| `observation.images.top` | 同一采样时刻的顶部 RGB | 是 |
| `observation.images.wrist` | 腕部 RGB | 是 |
| `observation.state` | 映射到真实接口语义的六维实际观测 | 是 |
| `action` | 同语义六维实际发送目标 | 训练监督；部署由策略输出 |
| `task` | 项目固定英文指令，由 writer 管理 task 索引 | 是，作为文本条件 |
| 来源与版本 | `source=sim`、模型/场景/专家版本、seed、layout、模板、参数 | 独立清单 |
| 诊断 | 物体真值、接触、阶段、失败码、成功与回放结果 | 独立诊断，不接入首版策略 |

六维向量的关节名称、单位、顺序与真实数据完全核对；当前 `use_degrees=true` 是项目候选设置，不代表已经完成实测。raw ctrl 与转换后的 action 同时保存，可核查往返映射和限位。模型需要的内部 padding 仍交给 π₀.₅ 实现，导出机器人接口保持六维。

### 7.3 使用框架 writer，不手写格式

当前本地源码候选为 LeRobot 0.6.2、提交 `d6039b8376a3ee099a6f0f64c1bb8599ca743ae3`。已静态核对该版本 `LeRobotDataset` 提供 `create`、`add_frame`、`save_episode`、`finalize`；逐帧写入要求包含 `task`。实现时使用该冻结版本实际 feature schema，不照抄其他版本的目录结构。

建议导出逻辑如下，属于流程伪代码，当前没有可执行导出脚本：

```python
dataset = LeRobotDataset.create(..., features=verified_features,
                               fps=verified_fps, video_backend="pyav")
try:
    for episode in qualified_episodes:
        for sample in episode:
            dataset.add_frame({
                "observation.images.top": sample.top_rgb,
                "observation.images.wrist": sample.wrist_rgb,
                "observation.state": sample.mapped_state,
                "action": sample.mapped_sent_target,
                "task": episode.instruction,
            })
        dataset.save_episode()
finally:
    dataset.finalize()
```

该版本 `finalize()` 负责刷新/关闭 writer，不能因看到了视频文件就认定数据已完整落盘。完成后从新进程重读数据，解码两路视频、检查首尾和关键动作帧，并加载一个真实训练 batch。

`video_backend="pyav"` 指重读后端，不自动解决写视频编码器问题；另做两路小视频写入与重读检查。当前项目的元数据检查工具不能替代全帧检查、动态回放或模型 batch 验证。[LeRobot 数据工具官方说明](https://huggingface.co/docs/lerobot/using_dataset_tools)

## 8. 数据规模、随机化与划分

按以下顺序扩大，前一层不通过就不启动后一层：

| 层级 | 目标 | 通过门槛 |
|---|---|---|
| 单布局 | 1 支牙刷、1 个杯、1 条完整成功 | 真接触、松爪稳定、控制回放 |
| 小批 | 少量新位置；可先争取 20 条合格轨迹 | 成功率/失败分布可解释、数据可重读 |
| 语言条件 | 2 支牙刷、2 个杯，四种组合 | 同布局换指令仍能选对物体与杯 |
| 初始训练候选 | 可先评估每条件 25～50 条，即 100～200 条合格轨迹 | 作为规模起点，按覆盖、质量和吞吐调整 |
| 扩展 | 更宽位置带、外观与适度物理变化 | 小批验证新参数后再批量生产 |

这些是采集目标，不是完成承诺；8h 原型窗口可能只足够达到第一层。条数也不直接等于多样性，重复模板产生的大量近似轨迹未必带来收益。

随机化逐项增加：

1. **几何布局：**已验证工作区内的牙刷 XY、小范围 yaw、杯间距；保持可行性与左右定义。
2. **视觉：**光照、桌面材质、背景干扰、相机小扰动；保持红/蓝身份可辨，匹配实物可能出现的变化。
3. **物理：**测量附近的小范围质量、摩擦、控制延迟等；每种新设置先检查接触与成功，不任意扩大。

不要把红牙刷固定放左、蓝牙刷固定放右，也不要把红永远指向左杯。对同一初态生成不同目标指令的独立完整 episode，可检验条件选择；所有相关变体使用共同 layout/group ID，划分时整组放同一侧。

分别统计 `reset尝试数 / 预检拒绝数 / 动态执行数 / 成功数 / 回放通过数 / 最终合格数`，按指令、位置区间和模板分层汇总。可达性拒绝会收缩任务分布，因此报告实际覆盖范围，不能只展示筛选后的成功比例。

sim 与 real 分别按整条 episode/group 划分训练和验证；同初态不同指令、相近布局、相同轨迹重渲染的变体不能分散到两侧。真实最终测试布局和结果不用于反复调仿真生成范围。

## 9. 建议的代码模块

以下是后续实施时的职责划分，当前只作为目录设计。仿真依赖保持在可选入口，不让普通项目准备工具或离线测试自动导入 MuJoCo。

```text
sim/washstand/
  assets/                 # 固定来源的 SO101 与自建物体资产、许可证、来源记录
  scene.xml               # 桌面、机器人、对象、相机
  scene_config.json       # 尺寸、工作区、采样范围、接触参数、版本
  env.py                  # reset / observe / step_targets / render
  control.py              # 命名索引、真实接口映射、限幅、时间调度
  kinematics.py           # 独立探针 IK、姿态模板与路径可行性检查
  expert.py               # 状态机；只产出控制目标
  validators.py           # 抓取、入杯、稳定与异常检查；独立于专家
  recorder.py             # 原始轨迹、状态快照、诊断记录
  generate.py             # 按 seed/指令批量运行与汇总尝试
  replay.py               # 只依赖保存控制序列的动态回放
  export_lerobot.py        # 合格清单 → LeRobot writer
  inspect.py              # 视频、曲线、关键帧和检查汇总
```

建议最小环境接口是 `reset(seed, task, params)`、`observe()`、`step_targets(target)`、`render(camera)`；导出器与专家解耦。规划器不能直接替 recorder 写“成功动作”，成功判定器也不能读取专家的内部完成标志来跳过验证。

## 10. 实施顺序和停止条件

### 首次原型：最多 8h，来自主线节余

| 检查窗口 | 重点 | 可验收产物 |
|---|---|---|
| 0～1h | 资产来源、加载、关节与图形环境 | 版本记录、场景加载截图、问题记录 |
| 1～3h | 桌面/物体/双相机/六维接口 | 两路图像、落杯测试、控制与索引检查 |
| 3～6h | 一套可达姿态模板与单次专家 | 抓取或失败视频、阶段日志；争取完整成功 |
| 6～8h | 回放、数据记录、最小重读 | 有成功则验证一条；否则交付明确问题与原型 |

这是检查顺序和时间盒，不是每项必定可完成的工时估计。若某项持续失败，保留证据，不因临近 8h 而使用虚拟夹持或放宽成功判定。达到上限后回到真实主线；完整自动化、20 条轨迹、四种条件、批量导出和训练对照另行排期。

### 后续扩展：逐项通过，不预填完成状态

- [ ] 单布局完整动作经物理执行、释放稳定、控制回放验证。
- [ ] 成功检查器通过正反例，杯/牙刷接触模型经检查。
- [ ] 两路 RGB、state/action、时间戳与真实接口语义一致。
- [ ] 小批轨迹可重读，首尾/关键帧和动作曲线人工确认。
- [ ] 四种指令和布局范围均有覆盖，失败原因可汇总。
- [ ] LeRobot 数据与训练 batch 检查通过，训练集统计来源明确。
- [ ] 仿真小批吞吐、磁盘量和实际开发工时已测量。
- [ ] 在真实基线完成后才增加联合训练与额外真机对照。

生成耗时用小批实测推算：`所需尝试数 ≈ 目标合格数 / 实测合格率`，再乘每次尝试的墙钟耗时，加编码和校验开销。分别记录“无图像物理”“双相机采集”“编码导出”和“回放验证”的速度；没有实测前不承诺一小时能生成多少条。

## 11. 如何接入后续训练与展示

先固定 Real-only 的真实训练子集，再从同一 π₀.₅ 基础权重增加 Sim+Real 对照。两域六维动作、相机语义和时序通过检查后，采用显式来源采样；初始可试 real:sim=1:1，不按目录里的总帧数决定比例。

主对照尽量固定真实数据、可训练参数、处理器和统计方案。可先由 real-train 拟合公共统计用于两域，并检查仿真超范围/裁剪；验证与测试不参与拟合。阶段式 Sim→Real 是后续另一组实验，不要求为了使用仿真先加一个单独训练阶段。详细变量与对照规则见 [可选仿真与联合训练](可选仿真与联合训练.md)。

仿真最值得展示的工程证据包括：场景与实物对应、失败可追溯的自动专家、只用控制目标的回放、可重读数据和真实对照。若尚未做联合训练，就展示“数据管线原型”，不声称已经实现 sim-to-real；若真机对照没有提升，同样记录结果和可能原因。

## 12. 当前结论与下一步

方案已经明确：先用有限工作区和可达姿态模板做真实接触专家，再扩展随机布局与语言条件；每条训练候选轨迹经历独立成功检查、动作回放和数据重读。当前完成的是本文设计，仿真实现和迁移效果都未验证。

下一步仍为主线 G0/G1 的实物测量、相机/单位确认和少量人工可行性示范。它们同时为仿真提供尺度与模板，避免搭建与真实装置脱节的环境。达到主线 G2、确有节余后，再按第 10 节开始本地原型。
