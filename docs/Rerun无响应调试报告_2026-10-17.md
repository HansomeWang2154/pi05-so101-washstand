## 22:13真机重试的补充结论

用户使用关闭显示压缩的脚本实际运行至22:17:30，控制测量256.5秒、29.90Hz；用户确认top/wrist画面及窗口均持续正常。因此该显示绕过已获得本次真机运行验证，不再仅是离线图片证据。退出时从臂id2关力矩失败及native abort归ISSUE-019，不是此前JPEG显示卡住的复发。

新出现的Rerun `Exceeded gRPC proxy server memory...dropping...`为INFO：0.33.1默认代理缓存1GiB，逐条缓存静态图像消息，超限先回收旧时间消息、再回收旧静态消息。它与viewer只保留实体最新静态图像的存储策略不同，主要影响后来连接的客户端可获得的历史/完整静态集合；不能直接推出当前控制失败、系统内存耗尽或录制文件丢失。

以两路640×480 RGB、每循环发送一次、目标30Hz估算，未压缩像素负载约55.3MB/s，尚未计协议开销。这个估算解释了缓存为何容易到上限，不是实测相机新帧率或USB带宽。`LEROBOT_RERUN_MEMORY_LIMIT`调整的是viewer层，不能当作代理默认缓存的控制变量；本轮没有盲目加大内存或重新开启JPEG。后续可单独验证显示降频/重复帧去重，不直接改变机械臂控制频率。

SOCKS提示表示该Rust HTTP客户端未编入相应代理支持，不能通过随意安装Python代理包解决；日志不足以确定触发它的外网请求。JPEG解码告警残片仍可能出现在腕相机MJPG采集链，关闭的是向Rerun发送图片时的再次压缩。日志交织，不能确定其相机来源或将其作为退出崩溃原因。

原始日志与用户现场反馈归档于`outputs/real/real_20261017_221308_teleop_review/`。[0.33.1代理缓存实现](https://github.com/rerun-io/rerun/blob/0.33.1/crates/store/re_grpc_server/src/lib.rs)支持上述回收机制；这不是G0全部验收或G1真实数据证据。

## 结论与现场处理

用户确认重接腕相机后机械臂跟随正常，但桌面提示 Rerun“程序无响应，请等待”。本机对照定位到 `rerun-sdk==0.33.1` 的 JPEG 压缩显示路径：同样的最小双图布局，开启显示压缩时未完成显示截图，关闭后可以显示。底层具体阻塞函数尚未定位，不能直接宣布显卡、Wayland 或相机损坏。

本机启动器已将 `--display_compressed_images=true` 改为 `false`。该参数控制 LeRobot 向 Rerun 发送的图像表示；**腕相机采集仍用 MJPG，top 仍用 YUYV**，相机格式、标定和动作参数没有改变。

用户重试顺序：先支稳从臂，在遥操作终端按 Ctrl+C，关闭旧的无响应 Rerun 窗口，再运行：

```bash
conda activate lerobot
bash outputs/real/real_20261017_162848_camera_debug/teleoperate-with-cameras.sh
```

Rerun SDK 会复用已占用默认端口的旧 viewer，重启控制程序并不保证换掉旧卡住窗口。不能只让旧窗口一直等待，也不要并行启动第二个机械臂/相机流程。缺设备启动预检和此前的线缆走线要求仍适用。
