## 使用规则

- 新问题依次编号 `ISSUE-001`、`ISSUE-002`；同一问题复发时更新原条目并追加日期，不覆盖历史。
- 先写环境、现象、复现方式和原始证据，再写判断；区分已确认原因、推测和仍未知的部分。
- 状态使用：待排查、处理中、已绕过、已解决、已解释。绕过方案可用不等于根因已修复。
- 解决后补上验证命令、实际结果、适用范围和回顾要点。未知信息保持“待确认”。
- 关联代码提交、配置、数据版本和实验ID；日志存文件，在此保留关键摘要和链接，不粘贴凭据。
- 文档中的待核实事项不自动表示代码或硬件存在故障。

## ISSUE-001：TorchCodec 动态库加载警告

- **环境：**项目 `.venv`，Python 3.12.14，PyTorch 2.11.0，LeRobot 0.6.2。
- **现象：**运行 LeRobot 训练模块的帮助入口时，出现 `Could not load libtorchcodec`。帮助命令仍返回 0。
- **复现：**在项目环境运行 `python -m lerobot.scripts.lerobot_train --help`。
- **已确认：**日志包含缺少某些版本的 `libavutil`，以及某个候选加载路径的 `CXXABI_1.3.15` 不满足。TorchCodec 会尝试多个 FFmpeg 版本，不能将每条尝试失败都当成独立故障。
- **根因结论：**完整的动态库/版本兼容根因尚未定位，没有修改系统库或原有环境。
- **处理：**训练命令预览显式选择 `dataset.video_backend=pyav`。
- **验证：**PyAV 15.1.0 成功写入并重新解码 4 帧 32×32 H.264 合成视频。
- **当前状态：**已绕过。合成小测不代表真实相机、全部编码或正式数据读取均通过；使用 PyAV 也不保证启动时不再打印 TorchCodec 警告。
- **后续：**G1 对实际视频解码检查；若需要 TorchCodec，再针对实际 FFmpeg/PyTorch 组合处理。
- **回顾要点：**包版本存在、动态库可加载和视频可解码是不同层次的验证。
- **证据：**[原始警告](../environment/lerobot-train-help.stderr.txt)、[CLI结果](../environment/lerobot-cli-check.local.json)、[PyAV小测](../environment/video-smoke.local.json)。

## ISSUE-002：当前工具环境中 GPU 查询失败

- **环境：**项目初始化时的工具执行环境。
- **现象：**`nvidia-smi` 返回 9，提示无法与 NVIDIA 驱动通信。
- **复现：**`washstand doctor --gpu`，或直接运行 `nvidia-smi`。

- **处理：**如实记录为未验证，没有自动重装驱动或更换 CUDA。
- **当前状态：**待排查。
- **后续：**在实际开发终端核对 `nvidia-smi`；在选定解释器中核对 PyTorch CUDA 是否可用，再做小张量计算。
- **回顾要点：**工具环境的可见性与物理机器的能力不能直接等同。
- **证据：**[环境检查报告](../environment/doctor.local.json)中的 `gpu` 字段。

## ISSUE-003：当前工具环境未发现机械臂串口和相机

- **环境：**初始化检查；用户已确认有 SO101 主从臂、顶部和腕部相机。
- **现象：**检查时 `/dev/ttyACM*` 和 `/dev/video*` 清单为空。
- **检查范围：**当前工具只列出这两种路径，没有穷尽所有串口类型、稳定别名或网络设备。
- **尚未知：**检查时设备是否连接、映射到当前会话、使用其他路径，或是否存在权限问题。
- **处理：**设备编号保持 `null`，不猜测串口和相机编号。
- **当前状态：**待确认，不是已证实的硬件故障。
- **后续：**在实际采集会话中确认主从臂端口、top/wrist画面、稳定设备路径和权限，再填写 `configs/local.json`。
- **验证标准：**主从设备对应正确；两路图像身份正确，能够稳定读取；之后再进行校准与遥操作检查。
- **回顾要点：**设备路径为空时先确认连接和检查范围，不应立即归因于驱动或硬件损坏。
- **证据：**[环境检查报告](../environment/doctor.local.json)中的 `device_paths`，以及[本机配置示例](../configs/local.example.json)。

## ISSUE-004：包已安装，但找不到 LeRobot 启动命令

- **环境：**项目 `.venv` 使用 `--system-site-packages` 复用已有 LeRobot 环境。
- **现象：**当前解释器能读取 LeRobot 0.6.2 的包元信息，但 `doctor` 的 PATH 检查未找到 `lerobot-train`、`lerobot-record`。
- **原因：**继承已有环境的包搜索路径，不等于把该环境的 console scripts 一并复制到新 `.venv/bin` 或加入当前 PATH。
- **处理：**项目生成 `python -m lerobot.scripts.lerobot_train`、`python -m lerobot.scripts.lerobot_record` 等模块入口预览；使用激活后的项目解释器。
- **验证：**训练模块 `--help` 返回 0；模块命令预览生成通过离线测试。数据采集模块未因此完成真实录制验证。
- **当前状态：**已绕过，未修补全局 PATH。
- **后续：**云端按冻结版本独立安装运行时；不把本机 `.venv` 直接复制过去。
- **回顾要点：**Python包能被找到，与shell命令能被找到是两回事。
- **证据：**[环境检查](../environment/doctor.local.json)、[训练CLI检查](../environment/lerobot-cli-check.local.json)、[命令预览实现](../src/washstand_vla/planning.py)。

## ISSUE-005：项目内为什么没有 lerobot 文件夹

- **提问背景：**项目目录中能看到自己的配置和工具，但没有 LeRobot 源码。
- **已确认：**当前使用的是可编辑安装，源码位于 `$LEROBOT_SOURCE`；包入口位于其 `src/lerobot/__init__.py`，版本 0.6.2。
- **设计：**本项目负责任务配置、数据准备、实验与部署接入；LeRobot作为外部依赖提供模型、训练、采集和机械臂驱动，没有复制第三方源码到本项目。
- **验证方式：**项目解释器中查询 `importlib.util.find_spec('lerobot').origin` 与包元信息。
- **当前状态：**已解释，无需为此重新克隆或搬动现有源码。
- **后续：**本地与云端记录相同的LeRobot版本/提交；云端同时准备项目和外部框架，不能依赖本机绝对路径。
- **回顾要点：**应用项目、框架源码、Python运行环境、模型权重是不同内容。
- **参考：**[目录与架构](项目总体规划.md)、[环境与协作](环境与本地云端协作.md)。

## ISSUE-006：如何搭建入杯场景并自动生成专家数据

- **提问背景：**用户希望把本地仿真作为可选部分，需要明确环境与专家数据来源。
- **已确认：**旧SO101抽纸巾示例使用虚拟夹持和位置约束IK；它不能作为新入杯任务的合格物理专家。SO101是五个手臂关节加夹爪，需要验证完整动作链可达性。
- **设计结论：**本地MuJoCo、空腔杯、自由刚体牙刷、可达姿态模板和状态机专家；通过独立成功检查、控制目标回放、数据重读后再纳入训练候选。
- **验证范围：**已静态检查旧代码、官方模型/物理说明和本地LeRobot writer接口；尚无本项目动态场景、专家成功或迁移效果证据。
- **当前状态：**已解释，实现待验证；这是一项设计疑问，不是已发生的硬件故障或已修复的仿真错误。
- **后续：**先完成实物测量、人工任务可行性和真机G2；有主线节余后进入最多8h原型探索，后续扩展另计工时。
- **回顾要点：**专家可以用物体真值规划，策略仍只用真实可获得的观测；外观成功、物理成功、可回放数据和真机迁移效果需要分别验证。
- **方案与依据：**[仿真环境与专家数据生成方案](仿真环境与专家数据生成方案.md)。
